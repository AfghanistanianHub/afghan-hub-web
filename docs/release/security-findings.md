# Scoped security and dependency evidence

This is a focused dependency and authorization-boundary review, not a completed exhaustive security scan. No production rows, schema, RLS policies or authentication settings were changed.

## Patched inherited runtime advisories

**Sharp 0.35.4 → 0.35.5**, through Next 16.3.8's optional image optimizer, was affected by high-severity [GHSA-wq5f-xc86-pv6w](https://github.com/advisories/GHSA-wq5f-xc86-pv6w), concerning bundled librsvg and CVE-2026-96889. Exploitation requires the affected SVG decoding path and environment. The current avatar control and storage MIME allowlists accept JPEG/PNG/WebP; no enabled arbitrary remote image patterns or SVG optimizer opt-in was found in Next configuration. This reduces an obvious user-upload attack path but does not prove all decoder paths unreachable. Sharp and its matching native/libvips optional packages were patched together without upgrading Next or changing top-level dependency ranges. The patch supports the repository's Node 22/24 targets; clean dependency installation and production builds passed on Node 22 and 24 CI.

**source-map-js 1.2.1 → 1.2.2**, through Next/PostCSS and Tailwind/PostCSS, was affected by high-severity [GHSA-68fv-2mgg-jv7q / CVE-2026-93749](https://github.com/advisories/GHSA-68fv-2mgg-jv7q). Malformed indexed source maps can exhaust CPU. Source-map processing is primarily a build/tooling path here; no endpoint accepting user-supplied source maps or application use of `SourceMapConsumer` was found. A malicious build dependency/input remains a relevant exposure. The patch changes the transitive lock entries only, preserving optional WASM dependencies and application versions.

After clean `npm ci`, `npm audit --omit=dev` reports **zero runtime findings**. This is advisory-database evidence, not proof that the application has no vulnerabilities. The full installation audit still reports nine high-severity development package nodes: @next/eslint-plugin-next, eslint-config-next, @shadcn/registry, @ts-morph/common, braces, fast-glob, micromatch, shadcn and ts-morph. npm suggests major downgrades for the root development packages, whose compatibility has not been qualified; do not use an uncontrolled `npm audit fix --force`.

## Authorization review

Read-only Supabase metadata confirmed RLS enabled on profiles, connections, conversations, conversation_members, messages, notifications, businesses, organizations, opportunities and events. Public catalog policies allow published records only. Profile discovery remains authenticated, public and onboarded; private profiles remain hidden. Message reads/inserts require membership, with inserts additionally requiring the authenticated sender ID. Connections are limited to participants/admins. Notification access is recipient scoped. Catalog writes remain owner/moderation scoped.

The reviewed live SECURITY DEFINER functions have empty `search_path` and explicit guards: `admin_list_member_accounts` and `set_profile_role` require admin; `get_my_access_context` and `get_message_inbox` scope to `auth.uid()`; `mark_notification_read` requires recipient; `respond_connection_request` requires the pending recipient; `start_direct_conversation` requires authentication and an accepted relationship. Decline removes the pending connection, and unauthorized responses return false. These contracts inform the isolated integration assertions.

Supabase advisors returned 20 authenticated SECURITY DEFINER exposure warnings. Their existence alone is not 20 proven vulnerabilities: these functions are intentionally part of the authenticated API and need individual guard review. The inspected subset has guards; remaining functions still need dynamic persona coverage. Advisor [remediation guidance](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable) remains relevant. Leaked-password protection is disabled in production, a confirmed configuration warning. Changing that production authentication setting is outside this authorization; the owner should review [password-security guidance](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection).
